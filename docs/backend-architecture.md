# 后端边界与维护约定

## 依赖方向

`cutin` 提供循环、工具与插件基础设施；`loopra/bin` 实现 Agent、项目与配置能力；`loopra/web` 负责 HTTP、SSE 和应用编排。

`bin` 不得依赖 `web`。核心需要访问项目运行时能力时，通过 `ProjectRuntimeAccess` 接口接入；用量与 token 速率通过 `AgentOutput` 和 `TokenSpeed` 输出，由 `SseAgentOutput` 转换成既有 SSE 事件。核心代码无需识别 SSE 实现类。

`UsageReporter` 和 `SessionLifecycle` 仅接收所需回调与动态依赖供应器。新增协作者时应列出实际需要的能力，避免把完整 `AgentLoop` 作为通用上下文传入。

## 聊天任务与会话

- `ChatController` 校验输入、准备消息、创建输出并调用应用服务。
- `ChatTaskService` 拥有后台执行器、请求登记、取消和完成回调。默认最多同时执行 16 个请求，额外排队 64 个；重复活动请求 ID 被拒绝，队列满时返回明确错误。
- `SessionAgentRegistry` 拥有 Agent 缓存、会话锁和活动请求集合。同一会话串行执行，不同会话使用独立锁；锁在缓存淘汰后保持身份，避免等待者与新请求使用不同锁。
- `SessionAgentFactory` 负责从已解析的模型设置创建 Agent，连接执行环境、共享工具系统、会话存储和 Web 用量监听器。
- `SessionTurn` 负责单次执行的会话锁、日志上下文、输出恢复、耗时写入与数据保存，通过 `try-with-resources` 保证收尾。
- `SessionSettingsService` 负责模型设置的优先级、渠道校验和会话元数据读写。
- `SessionUsageService` 负责已选择 Agent 的 token、上下文和费用视图；`UsageCostCalculator` 统一价格选择与费用拆分。
- `ProjectCapabilitiesService` 负责项目 Skill/MCP 摘要、手动刷新和延迟刷新的协调状态。
- `AgentService` 负责业务编排和缓存实例的选择，通过登记表查询会话状态和释放实例。

任务先登记再入队，因此排队请求也能被查询和取消。取消未开始任务会立即清理；取消运行中任务会发送中断，等待执行逻辑及其 `finally` 退出后再注销请求和关闭 SSE。完成回调只执行一次。先到达的取消请求保留最多五分钟，标记数量最多 1024 个。

缓存优先淘汰没有活动任务、没有持锁请求、也未运行的实例。繁忙会话允许暂时超过缓存目标容量，以保持停止请求可达。淘汰、清空和服务销毁均调用 Agent 的 `dispose()`，释放插件资源。已有会话锁保留至登记表销毁，内存占用随该进程访问过的会话数增长。

## Agent 创建与模型切换

模型、渠道和思考强度逐字段按“请求值 → 会话元数据 → 缓存 Agent → 全局默认值”解析。显式请求不存在的渠道会报错；历史渠道已被删除时回退到默认渠道。仅当解析结果改变时才回写会话元数据，每次读写结束均关闭临时 Store。

同一渠道内切换模型时复用 Agent，并更新模型输出限制和思考强度。跨渠道切换会保存会话、从缓存移除并释放旧实例，再由工厂按当前配置重建和恢复历史。重建失败时缓存保持为空，后续请求可以重试，不会拿到已经释放的 Agent。

工厂接收明确的配置和少量创建能力，不接收整个 `AgentService`。执行环境与工具系统使用同一个 `SessionEnvironment`，确保隔离分支的文件根与主项目状态根保持一致。缓存和请求互斥仍由调用方负责。

同步聊天、SSE 聊天、定时任务、需求执行和需求审批恢复统一使用 `SessionTurn`。作用域从已解析的会话键获取项目路径和会话名，未显式传入项目时使用与 Agent 相同的默认项目。只有绑定成功获取的 Agent 后才执行持久化；记录的耗时覆盖本轮新增的 assistant 消息，旧消息不重写耗时。

收尾分别尝试输出恢复、耗时写入、消息刷新和用量保存。普通运行时异常不会阻止后续步骤，日志上下文和会话锁始终在 `finally` 中恢复；多个收尾异常保留为 suppressed 异常，原始执行异常由 `try-with-resources` 保留。解锁后尝试项目延迟刷新，后台聊天仍要等已登记请求注销。SSE 的结束在外层 `finally` 中执行，因此准备回合或持久化失败也会结束流。这里只保证清理顺序与锁释放，不保证失败写入的数据已经落盘。

## 项目 MCP 刷新

`mcprefresh` 工具仅登记刷新意图，避免关闭当前回合仍在使用的连接。项目最后一个后台任务结束，或同步聊天、定时任务、需求执行释放会话锁后，再尝试执行。手动刷新遇到排队任务、运行中的 Agent 或持有会话锁的请求时会报错，检查完成前不会部分释放项目资源。

刷新、Agent 创建、配置重建和后台任务登记共用运行时协调锁；刷新还会临时持有该项目已知的会话锁。因此新任务会等待刷新完成后登记，已经拿到会话锁但尚未进入推理循环的请求也能阻止刷新。项目能力读取同样通过协调锁，避免读取正在被关闭的 provider。

刷新会释放本项目 Agent，移除共享工具缓存，关闭项目根及 worktree 执行根对应的 MCP provider，再重新读取能力摘要。缓存中的旧 worktree 即使已经没有 Agent，也会参与连接回收。工具系统缓存键使用规范化的 `SessionEnvironment`，不使用路径字符串前缀匹配，因此目录名中的 `#` 不会造成项目串扰；默认项目启动和后续会话也使用相同的键。

同一项目的重复登记会合并。每次登记带有独立身份，旧刷新结束或失败时只移除自己处理的登记，保留刷新期间新到达的请求。非繁忙状态下的自动刷新失败会记日志并移除失败登记，用户可重新登记或手动刷新。

## HTTP 与 SSE 错误

聊天参数校验发生在建立 SSE 和写入粘贴内容之前。空消息需附带图片；`execute_plan` 可以不带消息。未知 action 和 mergeMode 返回 400，未配置模型返回 503。

SSE 建立前，`ServiceException` 的状态码和公开说明进入普通 API 响应；未知异常记录完整服务端日志，对外仅返回通用说明。建立 SSE 后，任务提交和执行错误通过 `error` 事件传达，再结束输出。客户端需要保留处理 SSE `error` 事件的逻辑。

`SseEmitter` 发送和结束流共用互斥锁，正常结束时先发送一次 `done` 事件，再标记完成并关闭输出。重复或并发结束不会重复发送事件，结束后的消息不再写入。连接已经断开时仍完成等待信号。

## 用量和费用统计

`AgentService` 仅负责选择会话 Agent，再交由 `SessionUsageService` 组装用量视图。存在按模型保存的用量时分别计价；旧格式只有总量时按当前模型计价，同样拆分非缓存输入、缓存输入和输出费用。价格优先使用非空的用户配置，缺失或空配置才查询模型元数据；显式零价仍表示已知价格。价格查询失败仅影响对应模型的费用，token 与上下文数据继续返回，服务端保留错误日志。

费用按当前价格配置估算。输入 token 总量已包含缓存命中量，计算时扣除缓存部分后分别计费；负数计数按零计算，缓存命中量不超过输入量，无效费率按零处理。模型和日期汇总先保留原始精度，最终视图才四舍五入到四位小数，因此总费用可能与已舍入的每日费用之和有微小差异。

`DashboardService` 显式接收日志路径、时钟和价格来源，生产默认使用系统时区及用户用量日志。日统计、模型汇总和请求数使用相同的闭合日期范围（起始日至今天），未来日期记录和无法解析的记录不计入当前统计。每次查询为各模型解析一次价格，后续按日及模型汇总复用该结果。

## 配置持久化

更新和删除配置先在副本上应用改动，写入成功后再发布内存状态。保存使用同目录临时文件和原子替换；文件系统不支持原子移动时退回普通替换，临时文件在 `finally` 清理。写入失败向调用方抛出异常，不再报告成功或提前修改当前配置。

此机制保证单进程内的更新串行化；它不提供多个 Loopra 进程同时写同一份配置时的协调。

## 验证

在仓库根目录使用 JDK 17 和 Maven 3.9+：

```bash
mvn -B -ntp -gs .workflow/maven-central-settings.xml -s .workflow/maven-central-settings.xml clean test
pwsh -File .workflow/check-agent-boundaries.ps1
git diff --check
```

`backend-checks.yml` 对 `dev`、`main`、`master` 的推送和 PR 执行 Windows / Linux 测试矩阵，并用 `jdeps` 检查编译后的 `bin → web` 依赖。`.editorconfig` 约定后续编辑格式；没有对历史文件做全仓格式化。

测试使用的 DJL 原生库缓存固定在 `loopra/target/test-native-cache`。它不随测试切换的 `user.home` 变化，避免 Windows 将仍被 JVM 加载的 DLL 放进 JUnit 每例结束时需要删除的临时目录；测试仍正常执行 tokenizer 和临时目录清理。

## 后续拆分范围

`AgentService` 保留对外接口和运行时编排；`ProjectCatalog` 负责项目路径解析、列表排序和关联上下文，仅通过会话键供应器读取旧缓存索引，不持有 Agent。`SessionTurn` 统一处理计划执行成功、未启动、异常与中断后的收尾：已有执行产物则消费计划，否则回滚本轮历史并恢复待审批状态。

`SharedContextStore` 的修改统一经过同一个持锁、快照、持久化及失败回滚入口；KV 与文档继续保持各自的数据结构。`GitCommandRunner` 拥有 Git 子进程的并行读流、输出限制、超时及资源回收，Git 操作和快照服务各自保留原有超时。`JarFiles` 复用插件与拓展包的来源校验、获取和摘要计算，两种扩展系统分别管理清单与加载生命周期。

`AgentService` 仍包含较多会话操作，后续拆分应继续围绕业务职责进行。当前已明确任务、缓存、Agent 创建、回合收尾、模型设置、用量计价、项目查询、项目 MCP 刷新、输出和配置的边界。运行时协调锁仍是应用级锁；需要提升多项目刷新吞吐量时，应先设计跨项目操作的锁顺序，再考虑改为按项目协调。
